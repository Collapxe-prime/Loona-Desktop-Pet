# Git и Dev

Обе папки находятся рядом в `outputs`:

- `Loona-Desktop` — Dev: работа в PyCharm, окружения, настройки, резервные копии,
  черновики и локальные сборки. Путь оставлен прежним для совместимости с IDE.
- `Loona-Desktop-Git` — корень Git-репозитория и готовое приложение: `LoonaDesktopPet.exe`,
  `_internal`, `assets`, `VERSION`. Python пользователю не нужен.
- `Loona-Desktop-Git/Loona-Desktop` — отдельная папка всех исходников, тестов,
  документации, рабочих кадров и скрипта сборки. Из корня репозитория исходники убраны.

```text
Loona-Desktop-Git/
  LoonaDesktopPet.exe
  _internal/
  assets/
  VERSION
  Loona-Desktop/       исходники, тесты, документация, build.py
  .git/               состояние Git сохраняется
  .github/            если настроено release manager
```

Служебные файлы GitHub/release manager, включая social-preview и готовые ZIP в `dist`,
сохраняются в существующих местах; синхронизация ими не управляет.

Основные изменения делайте в Dev. Для переноса готовых изменений из Dev:

Перед переносом нужна полная сборка текущей VERSION в Dev `dist`: `python build.py`.
EXE не изменяется от правки исходников: после изменения поведения сначала пересоберите
приложение. Синхронизация проверяет версию сборки, её контрольные суммы и совпадение кадров;
если сборки нет или кадры изменились, перенос останавливается до замены файлов.

```powershell
.\.venv\Scripts\python.exe sync_git_version.py
.\.venv\Scripts\python.exe sync_git_version.py --apply
```

Первая команда показывает добавления, обновления и точный список удаляемых файлов,
вторая создаёт точное зеркало управляемых исходников. Перед переносом сохраните
изменения, сделанные непосредственно в Git-копии: они будут заменены версиями Dev.

Полностью заменяется папка исходников `Loona-Desktop` и готовые `_internal`, `assets`,
EXE и VERSION в корне. В папку исходников приходят Python-файлы, документы из
`DOCUMENTS`, `tests`, `packaging` и рабочие кадры из списка сборки; кэши и черновики
не переносятся. Прежние Python-файлы, документы, `tests` и `packaging` в корне Git
удаляются при миграции. Корневые `.gitignore` и `.gitattributes` берутся из шаблонов
`packaging/repository.*`; файлы внутри исходников сохраняют собственные правила Dev.
Удалённые в Dev исходники и лишние файлы в управляемых директориях удаляются.
Ссылки/junction в управляемых путях
вызывают отказ до изменений. Сначала готовится временная копия на D, затем заменяются
управляемые пути; при ошибке проверки старые управляемые файлы восстанавливаются.

Не управляются `.git`, `.github`, `dist`, `release`, `releases`, `RELEASE-ARTIFACTS.json`,
файлы в корне с префиксами `social-preview`, `release`, `github`, `publish`, а также
прочие неуправляемые файлы/каталоги в корне (например, LICENSE или README.md).
Эти файлы принадлежат GitHub/release manager и не приходят из Dev. Для нового типа
исходника Dev явно расширьте `DOCUMENTS` или `source_files`. GitHub/release-данные держите вне управляемых
директорий. После синхронизации проверяются состав и SHA-256 каждого управляемого
файла, отсутствие устаревших файлов и неизменность неуправляемых файлов, включая `.git`.

Репозиторий не инициализируется автоматически. Коммиты, теги и публикация отдельно.

## Диск D

Кадры обеих версий, исходники, сборки и окружения лежат на диске проекта.
`build.py` направляет временные файлы, кэш pip и PyInstaller в `build` рядом с кодом;
при текущем расположении это диск D. Изменения переменных действуют только на сборку,
системные настройки Windows не меняются.

Для новых импортов и генераций используйте `assets` и рабочие каталоги Dev на D.
Ранее выданные пользователю GIF и исходники в Downloads не перемещались.
Внешний сервис генерации или сама IDE могут использовать собственный кэш на C;
сборочный скрипт не управляет этим кэшем. Python, уже установленный на C, также
сохраняет своё расположение. Само приложение не записывает новые ассеты на C.
Небольшие настройки и лог собранного приложения по умолчанию остаются в LOCALAPPDATA;
их при необходимости можно перенаправить через `LOONA_DATA_DIR`.
